# AI Gateway 2.0 support — design

## Context

`kong-claude-ai-gateway` currently walks a reader through 8 progressively
advanced modules for running Claude Desktop through Kong, using Kong Gateway
3.x's "AI Gateway 1.x" (the `ai-proxy-advanced` plugin, applied via `decK`
against a single long-running hybrid data plane).

Kong is shipping **AI Gateway 2.0** as a separate/forked binary with a
genuinely different resource model — `ai_gateway_model`/`ai_gateway_policy`/
`ai_gateway_vault`/etc, applied via `kongctl` rather than `decK`. This isn't a
config toggle on the existing modules; it's a different install and a
different declarative schema. Declan's repo is exactly the kind of reference
material that should exist for this, and the Kong Americas SE team's own AI
GW 2.0 shakeout (`ai-gateway-test-harness`, `se-poc-config-default`,
`aigw2.0-test`) is directly reusable ground truth for what actually works,
what's broken, and what the workarounds are — rather than re-discovering all
of it from scratch.

**Goal:** add a parallel AI Gateway 2.0 track to this repo, mirroring the
existing module structure, so a reader can stand up either stack and see
exactly what changes between 1.x and 2.0 per module — grounded in real,
live-verified behavior against a real Konnect org (the Fel Tech org, via
`KONNECT_TECH_TOKEN`), not assumptions.

## Repo structure

```
kong-2.0/                      # one kongctl YAML per module, cumulative (mirrors kong/)
  00-platform.yaml             # ai_gateway control plane + vault (new — no 1.x equivalent)
  01-general-proxying.yaml
  02-key-auth.yaml
  03-oidc-okta.yaml
  04-per-user-model-limits.yaml
  05-consumer-rate-limiting.yaml
  07-opentelemetry.yaml
docs-2.0/                      # one walkthrough per module (mirrors docs/)
  00-prerequisites-2.0.md
  01-general-proxying-2.0.md
  ...
docker-compose.aigw2.yml       # AI GW 2.0 hybrid DP overlay (kong/kong-ai-gateway-dev image),
                                # separate from docker-compose.yml
```

Module 6 (Konnect built-in observability) has no `kong-2.0/*.yaml` for the
same reason module 6 has none today — Admin-API-only, no decK/kongctl. Module
8 (metering & billing) stays "planned" in both tracks; not in scope here.

Tooling: **`kongctl`**, not `decK` — it's the tool actually gaining native
AI Gateway 2.0 resource support, matches where Kong is heading, and the SE
team's own shakeout material is already `kongctl`-native.

## Per-module plan

| # | Module | Plan |
|---|--------|------|
| 0 | Prerequisites | New doc: AI GW 2.0 control plane provisioning (`ai_gateways` resource, not a generic Gateway CP), `kongctl` install/auth, `.tech`-vs-`.com` Konnect environment callout (2.0 is pre-GA — state current status as observed against the Fel Tech org, not assumed). Vault becomes `ai_gateway_vault` (`type: konnect`), scoped per-resource rather than global. |
| 1 | General proxying | `ai_gateway_model` replaces service+route+`ai-proxy-advanced`. **Live-test against the Fel Tech org** with `formats: [anthropic]` — do not assume the 07-09/07-10 shakeout snapshot (KOKO-3854) still applies; Kong Eng indicated a fix was landing. Two `target_models` entries: direct Anthropic API key (primary, mirrors 1.x) and Bedrock-backed Claude (secondary/alternate). Status banner reflects the actual live result and build tested, with the shakeout finding cited only as prior context if it turns out to still apply. |
| 2 | Key auth | `key-auth` becomes a named `ai_gateway_policy` referenced from the model's `policies:` list (not inlined per-attachment like a 1.x plugin block). Verify live once module 1's model is confirmed working. |
| 3 | OIDC + Okta | Auth attaches via a first-class `identity_providers` entity referenced from `model.access.identity_providers` — **not** `policies:` (putting `openid-connect` under `policies:` silently fails the whole config conversion: 0 routes, CP still reports success). The shakeout found `openid-connect` decisions non-deterministic (~20-40% wrong either direction) against Kong Identity specifically — since this module brings a real customer-style Okta tenant (not Kong Identity), it's the one place worth closing out that open question live. |
| 4 | Per-user model limits | `pre-function` JWT-claim-to-header pattern is unaffected. The target `request-termination` static-model-list trick moves behind an `identity_providers`-gated model, inheriting module 3's auth pattern. |
| 5 | Rate limiting | `ai-rate-limiting-advanced` as a named policy — shakeout already verified this live (3.4, 3.5 cost-budget variant). Straightforward port; verifiable independent of module 1. |
| 6 | Konnect observability | Likely unaffected (Konnect-platform feature, not gateway-config). Confirm live that `push-konnect-dashboard.sh`'s Admin API calls work the same against an `ai_gateway`-type CP. |
| 7 | OpenTelemetry | `opentelemetry` policy config alone is not sufficient — traces need core DP env (`KONG_TRACING_INSTRUMENTATIONS=all`, `KONG_TRACING_SAMPLING_RATE=1.0`) in addition, or logs/metrics export but traces silently don't. Directly reusable finding from the shakeout (Issue 21, resolved). |
| 8 | Metering & billing | Out of scope (still "planned" in 1.x too). Note for later: `kongctl diff` on `ai_gateway_model`/`ai_gateway_policy` never converges to a clean "0 to change" (kongctl#1486, cosmetic) — relevant if a future `verify.sh`-style idempotency check gets added. |

Cross-cutting items to fold into whichever module doc is most relevant, not
their own module: `providers:` → `model_providers:` (kongctl dropped the
legacy key), and MCP/agent resources currently can't be created via `kongctl
apply` at all (kongctl#1499, workaround is the direct Konnect API) — noted
only if a future module needs MCP.

## Verification approach

- `KONNECT_TECH_TOKEN` (already in `~/.kong-se/secrets.env`) against the Fel
  Tech org is the source of truth. The SE team's shakeout scoreboard
  (`aigw2.0-test/AIGW-2.0-CRITERIA-PROGRESS.md`) is a **starting hypothesis**
  per module, not a fact to transcribe — confirm live, note where current
  behavior matches or diverges from that snapshot (with a date/build), citing
  it as prior art either way.
- After every `kongctl apply`, confirm the DP's compiled config (`GET
  :8001/config`) actually shows the expected chain (e.g. model →
  `ai-model-selector` → `ai-proxy-advanced`) — the shakeout's own findings
  note the Konnect CP can report success while the DP silently drops routes.
- Each `docs-2.0/NN-*.md` gets a status banner: verified date, `kongctl`
  version + AI Gateway image tag tested, and ✅ verified / ⚠️ workaround
  required / ❌ blocked (with tracking issue link). This ages visibly instead
  of going stale silently, same convention the shakeout scoreboard uses.

## Docs template addition

Each `docs-2.0/NN-*.md` follows the existing `docs/NN-*.md` template
(what it adds, config diff, apply command, Desktop app config change), plus:

- Status banner at the top (see above)
- A short "vs. 1.x" callout — the specific schema/behavior delta for that
  module
- Any workaround required, with its tracking issue link (KOKO-/AG-/kongctl#)

## Out of scope

- Module 8 (metering & billing) — still "planned" in 1.x, not addressed here.
- MCP/A2A resources — not part of any existing 1.x module, so not pulled in
  unless a later module needs them.
- Anything the shakeout marked as needing infra this repo doesn't have (e.g.
  module 3.6-style cloud-native auth needing an AWS-hosted DP with an IAM
  instance role) — noted as a known gap, not built around.
